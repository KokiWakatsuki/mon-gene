# Mon-Gene サービス責務定義書

## 📋 現在の3層構成の責務

Mon-Geneは**マイクロサービスアーキテクチャ**を採用しており、3つの独立したサービスで構成されています。

---

## 🎨 フロントエンド（front）

### 技術スタック
- **フレームワーク**: Next.js 15.5.2（TypeScript）
- **UIライブラリ**: React 19.1.0
- **スタイリング**: Tailwind CSS 3.4.0

### 主な責務

#### 1. ユーザーインターフェース（UI）
- **問題生成画面**: パラメータ設定、生成モード選択
- **問題一覧・検索画面**: 履歴表示、検索機能
- **プレビュー・編集画面**: 問題の確認・修正
- **設定画面**: AI設定、ユーザー情報管理

#### 2. ユーザー体験（UX）
- **リアルタイム進捗表示**: SSEによる生成プロセスの可視化
- **レスポンシブデザイン**: PC・タブレット・スマホ対応
- **インタラクティブ操作**: モーダル、アコーディオン、タブ切り替え

#### 3. クライアントサイドロジック
- **状態管理**: 問題データ、ユーザー情報、UI状態
- **バリデーション**: 入力値の事前チェック
- **データ整形**: APIレスポンスの表示用変換
- **数式レンダリング**: LaTeX記法の表示変換

#### 4. API通信
- **RESTful API呼び出し**: バックエンドとの通信
- **SSE接続管理**: リアルタイム進捗受信
- **エラーハンドリング**: ユーザーフレンドリーなエラー表示
- **認証管理**: トークンの保存・送信

#### 5. ファイル処理
- **ファイルアップロード**: PDF・テキストファイルの読み込み
- **プレビュー表示**: アップロードファイルの内容確認
- **印刷機能**: ブラウザ印刷ダイアログの制御

### フロントエンドが**やらないこと**
❌ ビジネスロジックの実装（問題生成アルゴリズム等）  
❌ データベースへの直接アクセス  
❌ AI APIの直接呼び出し  
❌ 図形生成処理  
❌ PDF生成処理  

---

## ⚙️ バックエンド（back）

### 技術スタック
- **言語**: Go 1.24.0
- **データベース**: MySQL 8.0
- **アーキテクチャ**: レイヤードアーキテクチャ + リポジトリパターン

### 主な責務

#### 1. ビジネスロジック
- **問題生成フロー制御**: 5段階生成、3問生成の全体制御
- **生成戦略の選択**: ユーザー設定に基づく生成方式の決定
- **パラメータ検証**: OpinionProfileV2の妥当性チェック
- **利用制限管理**: 生成回数、プレビュー回数の制御

#### 2. AI統合・オーケストレーション
- **AI API呼び出し**: Claude、GPT、Geminiへのリクエスト
- **会話履歴管理**: 5段階生成での文脈保持
- **プロンプト生成**: ユーザー入力からAI用プロンプトの構築
- **レスポンス解析**: AIレスポンスからの問題文・解答・コード抽出
- **マルチモーダル処理**: 画像・PDFファイルのAI処理

#### 3. データ永続化
- **問題データ管理**: 生成した問題のCRUD操作
- **ユーザー管理**: 認証情報、設定、利用状況の管理
- **検索機能**: キーワード検索、パラメータ検索、複合検索
- **会話履歴保存**: 5段階生成プロセスの全履歴保存

#### 4. 認証・認可
- **ログイン処理**: 塾コード認証
- **セッション管理**: トークン発行・検証
- **パスワード管理**: ハッシュ化、リセット機能
- **アクセス制御**: ユーザーごとのデータ分離

#### 5. 外部サービス連携
- **Coreサービス呼び出し**: 図形生成、PDF生成のリクエスト
- **メール送信**: パスワードリセット等の通知
- **ファイル処理**: PDFテキスト抽出（Google Files API経由）

#### 6. リアルタイム通信
- **SSE配信**: 生成プロセスの進捗イベント送信
- **進捗管理**: 各段階の完了通知
- **エラー通知**: 生成中のエラーの即時通知

#### 7. エラーハンドリング
- **AI APIエラー処理**: トークン制限、レート制限の適切な処理
- **ビジネスエラー**: 利用制限、バリデーションエラーの処理
- **詳細なエラーメッセージ**: ユーザーへの分かりやすいフィードバック

### バックエンドが**やらないこと**
❌ UI表示ロジック  
❌ 図形の実際の描画処理（Coreに委譲）  
❌ PDFの実際の生成処理（Coreに委譲）  
❌ Pythonコードの実行（Coreに委譲）

## 🐍 コアサービス（core）

### 技術スタック
- **言語**: Python 3.11
- **フレームワーク**: FastAPI 0.104.1
- **描画ライブラリ**: matplotlib 3.8.2
- **PDF生成**: ReportLab 4.0.7

### 主な責務

#### 1. 図形生成
- **matplotlib描画**: Pythonコードによる数学図形の生成
- **カスタム図形**: AIが生成したPythonコードの実行
- **図形パラメータ処理**: 座標、サイズ、ラベル等の計算
- **画像エンコード**: Base64形式への変換

#### 2. 数値計算
- **Pythonコード実行**: AIが生成した計算プログラムの実行
- **数値計算**: NumPyを使用した数学計算
- **結果フォーマット**: 計算結果の整形・出力

#### 3. PDF生成
- **ReportLab統合**: 問題文・図形・解答のPDF化
- **レイアウト制御**: 問題と解答の配置調整
- **数式レンダリング**: LaTeX記法のPDF変換
- **画像埋め込み**: Base64画像のPDF統合

#### 4. 組版処理
- **Typst統合**: 高品質な数式組版（将来の拡張）
- **フォーマット変換**: 各種形式への変換

#### 5. 問題解析
- **図形必要性判定**: 問題文から図形の要否を分析
- **図形タイプ検出**: 必要な図形の種類を特定
- **パラメータ推定**: 図形生成に必要なパラメータの推定

### コアサービスが**やらないこと**
❌ ビジネスロジック（問題生成フロー等）  
❌ データベースアクセス  
❌ AI API呼び出し  
❌ 認証・認可  
❌ ユーザー管理

## 🔄 サービス間の連携フロー

### 問題生成フロー（5段階生成の例）

```
1. ユーザー操作
   フロント: パラメータ設定 → 生成ボタンクリック

2. API呼び出し
   フロント → バック: POST /api/generate-problem-five-stage-sse
   - 認証トークン
   - OpinionProfileV2
   - 生成モード

3. ビジネスロジック実行
   バック:
   - ユーザー認証・利用制限チェック
   - AI設定の取得（Claude/GPT/Gemini）
   - プロンプト生成

4. Stage 1-2: 問題構成・パラメータ設定
   バック → AI API: 問題構成生成リクエスト
   AI API → バック: 問題構成レスポンス
   バック → フロント: SSEイベント（Stage 1完了）
   
   バック → AI API: パラメータ設定リクエスト
   AI API → バック: 数値計算プログラム
   バック → コア: POST /execute-python
   コア: Pythonコード実行
   コア → バック: 計算結果
   バック → フロント: SSEイベント（Stage 2完了）

5. Stage 3: 図形生成
   バック → AI API: 図形コード生成リクエスト
   AI API → バック: Pythonコード
   バック → コア: POST /draw-custom-geometry
   コア: matplotlib で図形描画
   コア → バック: Base64画像
   バック → フロント: SSEイベント（Stage 3完了）

6. Stage 4-5: 問題文・解答生成
   バック → AI API: 問題文生成リクエスト
   AI API → バック: 完全な問題文
   バック → フロント: SSEイベント（Stage 4完了）
   
   バック → AI API: 解答生成リクエスト
   AI API → バック: 完全な解答・解説
   バック → フロント: SSEイベント（Stage 5完了）

7. データ保存
   バック → MySQL: 問題データ保存
   - 問題文、解答、図形（Base64）
   - OpinionProfileV2
   - 会話履歴

8. 結果表示
   バック → フロント: 完了イベント + 問題データ
   フロント: プレビューモーダル表示
```

### PDF生成フロー

```
1. ユーザー操作
   フロント: 印刷ボタンクリック

2. API呼び出し
   フロント → バック: POST /api/generate-pdf
   - 問題文
   - 図形（Base64）
   - 解答

3. PDF生成依頼
   バック → コア: POST /generate-pdf
   - 問題文
   - 図形データ
   - 解答

4. PDF生成
   コア: ReportLab でPDF生成
   - レイアウト調整
   - 数式レンダリング
   - 画像埋め込み

5. 結果返却
   コア → バック: Base64 PDF
   バック → フロント: PDF データ
   フロント: ブラウザで印刷ダイアログ表示
```

## 📊 責務の分離理由

### なぜ3層に分けるのか？

#### 1. 技術的な理由
- **言語の最適化**: 
  - Go: 並行処理、高パフォーマンス（ビジネスロジック）
  - Python: 科学計算、描画ライブラリが豊富（図形・計算）
  - TypeScript: 型安全なUI開発

#### 2. スケーラビリティ
- **独立したスケーリング**: 
  - バック: リクエスト数に応じて水平スケール
  - コア: 計算負荷に応じて独立スケール
  - フロント: CDN配信で高速化

#### 3. 保守性
- **責務の明確化**: 各サービスの役割が明確
- **独立した開発**: チームが並行して開発可能
- **障害の局所化**: 1つのサービスの障害が全体に波及しない

#### 4. 再利用性
- **コアサービスの汎用性**: 他のアプリケーションからも利用可能
- **APIの標準化**: RESTful APIで疎結合

## 🎯 改善後の責務（提案）

改善アーキテクチャでは、各サービス内部をさらに明確に分離します：

### バックエンド内部の4層
1. **ドメイン層**: ビジネスルール（問題生成ロジック）
2. **アプリケーション層**: ユースケース（生成フロー制御）
3. **インフラ層**: 外部連携（AI、DB、コア）
4. **プレゼンテーション層**: HTTP API

### フロントエンド内部の機能分離
1. **features/**: 機能別モジュール（problem, auth, settings）
2. **shared/**: 共有コンポーネント（UI、hooks、utils）
3. **lib/**: ライブラリ設定（API client、config）

### コアサービス内部の4層
1. **ドメイン層**: 図形・計算のビジネスルール
2. **アプリケーション層**: 描画・計算のユースケース
3. **インフラ層**: matplotlib、ReportLab等の実装
4. **プレゼンテーション層**: FastAPI エンドポイント

## ✅ まとめ

| サービス | 主な責務 | 使用技術 | 依存先 |
|---------|---------|---------|--------|
| **フロント** | UI/UX、状態管理、API通信 | Next.js + React | バック |
| **バック** | ビジネスロジック、AI統合、データ管理 | Go + MySQL | AI API、コア |
| **コア** | 図形生成、数値計算、PDF生成 | Python + FastAPI | なし |

この責務分離により、各サービスが独立して開発・デプロイ・スケールでき、
長期的な保守性と拡張性が確保されています。
