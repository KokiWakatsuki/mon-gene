# Mon-Gene 改善アーキテクチャ設計書 v3.0

## 📋 現状の課題

### コードの複雑性
- **problem_service.go**: 2435行（複数の責務が混在）
- **責務の不明確さ**: ビジネスロジック、AI呼び出し、データ変換が1ファイルに集約

### 保守性の問題
- **テストの困難さ**: 巨大なファイルのユニットテスト作成が困難
- **変更の影響範囲**: 1つの変更が広範囲に影響

### 拡張性の制約
- **新機能追加**: 既存コードへの影響が大きい
- **AI統合**: 新しいAIプロバイダーの追加が複雑

---

## 🎯 設計原則

1. **単一責任の原則（SRP）**: 1ファイル = 1つの明確な責務
2. **開放閉鎖の原則（OCP）**: 拡張に開いて、修正に閉じている
3. **依存性逆転の原則（DIP）**: 抽象に依存し、具象に依存しない
4. **YAGNI原則**: 必要になるまで実装しない

## 📐 レイヤー別の責務（簡潔版）

### 1. Domain層
**責務**: ビジネスロジックのみ  
**含むもの**: エンティティ、値オブジェクト、リポジトリIF、生成戦略  
**ルール**: 他の層に依存しない

### 2. Usecase層
**責務**: ユースケースの実装  
**含むもの**: ビジネスフローの調整  
**ルール**: Domainを使用、Infrastructureのインターフェースを使用

### 3. Infrastructure層
**責務**: 外部システム連携  
**含むもの**: リポジトリ実装、AIクライアント、外部API  
**ルール**: Domainのインターフェースを実装

### 4. Handler層
**責務**: HTTPリクエスト/レスポンス  
**含むもの**: ハンドラー、ミドルウェア  
**ルール**: Usecaseを呼び出すのみ

## 🎯 具体的な改善例

### 例1: 問題生成の分割（Before/After）

#### Before（2435行）
```go
// problem_service.go
type problemService struct {
    // 10個以上の依存関係
}

func (s *problemService) GenerateProblem(...) {...}        // 500行
func (s *problemService) GenerateProblemFiveStage(...) {...} // 800行
func (s *problemService) GenerateThreeProblems(...) {...}   // 600行
// ... 多数のメソッド
```

#### After（各ファイル200-300行）
```go
// domain/generation/strategy.go (20行)
type Strategy interface {
    Generate(ctx context.Context, req Request) (*Result, error)
}

// domain/generation/five_stage.go (300行)
type FiveStage struct {
    ai ai.Provider
}

func (s *FiveStage) Generate(ctx context.Context, req Request) (*Result, error) {
    // 5段階生成ロジックのみ
}

// usecase/generate_problem.go (100行)
type GenerateProblem struct {
    strategies map[string]generation.Strategy
    problemRepo domain.ProblemRepository
}

func (uc *GenerateProblem) Execute(ctx context.Context, req Request) (*Response, error) {
    strategy := uc.strategies[req.Mode]
    return strategy.Generate(ctx, req)
}
```

**改善点**:
- ✅ 各ファイルが単一の責務
- ✅ テストが容易
- ✅ 新しい生成方式の追加が簡単

### 例2: AI統合の統一

#### Before
```go
// 各クライアントが個別実装、サービスで分岐
switch user.PreferredAPI {
case "claude": ...
case "openai": ...
case "google": ...
}
```

#### After
```go
// infrastructure/ai/provider.go (30行)
type Provider interface {
    Generate(ctx context.Context, req Request) (*Response, error)
}

// infrastructure/ai/factory.go (40行)
type Factory struct {
    providers map[string]Provider
}

func (f *Factory) Create(apiType string) Provider {
    return f.providers[apiType]
}

// 使用側
provider := aiFactory.Create(user.PreferredAPI)
result, err := provider.Generate(ctx, req)
```

**改善点**:
- ✅ 分岐ロジックの削除
- ✅ 新しいAIの追加が容易
- ✅ テストが簡単

## 📝 実装ガイドライン

### ファイル構成の原則
1. **1ファイル = 1つの責務**
2. **最大500行**（理想は200-300行）
3. **関連する小さな型は同じファイルに配置可**

### 命名規則
- **エンティティ**: `Problem`, `User`
- **値オブジェクト**: `OpinionProfile`
- **ユースケース**: `GenerateProblem`, `SearchProblem`
- **リポジトリ**: `ProblemRepository`

### エラーハンドリング
```go
// shared/errors.go（1ファイルで十分）
type AppError struct {
    Code       string
    Message    string
    StatusCode int
}

var (
    ErrUnauthorized = &AppError{Code: "UNAUTHORIZED", StatusCode: 401}
    ErrNotFound     = &AppError{Code: "NOT_FOUND", StatusCode: 404}
)
```

### ロギング
```go
// shared/logger.go（1ファイルで十分）
type Logger interface {
    Info(msg string, fields ...zap.Field)
    Error(msg string, fields ...zap.Field)
}
```
