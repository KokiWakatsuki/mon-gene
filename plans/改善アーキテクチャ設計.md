# Mon-Gene 改善アーキテクチャ設計書

## 📋 現状の課題分析

### 1. コードの複雑性
- **problem_service.go**: 2435行の巨大ファイル
- **問題生成ロジック**: 複数の生成方式が1つのサービスに混在
- **責務の不明確さ**: ビジネスロジック、AI呼び出し、データ変換が混在

### 2. 保守性の問題
- **テストの困難さ**: 巨大なサービスクラスのユニットテスト作成が困難
- **変更の影響範囲**: 1つの変更が広範囲に影響
- **コードの重複**: 類似処理が複数箇所に存在

### 3. 拡張性の制約
- **新機能追加**: 既存コードへの影響が大きい
- **AI統合**: 新しいAIプロバイダーの追加が複雑
- **科目追加**: 数学以外への対応が困難

---

## 🎯 改善アーキテクチャの設計方針

### 設計原則
1. **単一責任の原則（SRP）**: 各モジュールは1つの責務のみを持つ
2. **開放閉鎖の原則（OCP）**: 拡張に開いて、修正に閉じている
3. **依存性逆転の原則（DIP）**: 抽象に依存し、具象に依存しない
4. **インターフェース分離の原則（ISP）**: 必要最小限のインターフェース
5. **ドメイン駆動設計（DDD）**: ビジネスロジックをドメイン層に集約

## 📐 レイヤー別の責務定義

### 1. ドメイン層（Domain Layer）
**責務**: ビジネスロジックの中核

**含むもの**:
- エンティティ（Entity）: IDを持つビジネスオブジェクト
- 値オブジェクト（Value Object）: 不変のビジネス概念
- ドメインサービス: 複数エンティティにまたがるロジック
- リポジトリインターフェース: データアクセスの抽象

**ルール**:
- 他の層に依存しない
- フレームワークに依存しない
- ビジネスルールのみを含む

### 2. アプリケーション層（Application Layer）
**責務**: ユースケースの実装

**含むもの**:
- ユースケース: 具体的な業務フロー
- DTO（Data Transfer Object）: 層間のデータ転送
- アプリケーションサービス: ユースケースの調整

**ルール**:
- ドメイン層を使用
- インフラ層のインターフェースを使用（実装は使わない）
- トランザクション境界を定義

### 3. インフラ層（Infrastructure Layer）
**責務**: 外部システムとの連携

**含むもの**:
- リポジトリ実装: データベースアクセス
- 外部APIクライアント: AI、メール等
- ファイルシステムアクセス
- キャッシュ実装

**ルール**:
- ドメイン層のインターフェースを実装
- 技術的な詳細を隠蔽
- 交換可能な実装

### 4. プレゼンテーション層（Presentation Layer）
**責務**: ユーザーインターフェース

**含むもの**:
- HTTPハンドラー
- リクエスト/レスポンス変換
- ミドルウェア
- バリデーション

**ルール**:
- アプリケーション層を使用
- HTTPの詳細を隠蔽
- 薄く保つ

```
Presentation Layer
       ↓
Application Layer
       ↓
Domain Layer
       ↑
Infrastructure Layer
```

**重要**: インフラ層はドメイン層のインターフェースを実装する（依存性逆転）

### 例2: AI統合の改善

#### Before
```go
// 各クライアントが個別に実装
claudeClient := clients.NewClaudeClient(model)
openaiClient := clients.NewOpenAIClient(model)
googleClient := clients.NewGoogleClient(model)

// サービスで分岐
switch user.PreferredAPI {
case "claude":
    content, err = claudeClient.GenerateContent(ctx, prompt)
case "openai":
    content, err = openaiClient.GenerateContent(ctx, prompt)
// ...
}
```

#### After
```go
// infrastructure/ai/provider.go
type Provider interface {
    Generate(ctx context.Context, req GenerateRequest) (*GenerateResponse, error)
    GenerateWithHistory(ctx context.Context, history []Message) (*GenerateResponse, error)
    SupportsMultimodal() bool
}

// infrastructure/ai/factory.go
type Factory struct {
    providers map[string]Provider
}

func (f *Factory) Create(apiType, model string) (Provider, error) {
    provider, exists := f.providers[apiType]
    if !exists {
        return nil, ErrUnsupportedProvider
    }
    return provider.WithModel(model), nil
}

// application層での使用
provider, err := aiFactory.Create(user.PreferredAPI, user.PreferredModel)
if err != nil {
    return err
}
result, err := provider.Generate(ctx, req)
```

## 📝 実装ガイドライン

### 命名規則
- **エンティティ**: 名詞（Problem, User）
- **値オブジェクト**: 名詞（OpinionProfile, GenerationMode）
- **サービス**: 動詞+Service（GenerationService）
- **ユースケース**: 動詞+UseCase（GenerateProblemUseCase）
- **リポジトリ**: エンティティ名+Repository（ProblemRepository）

### ファイル構成
- 1ファイル = 1つの主要な型または機能
- 最大500行を目安
- 関連する小さな型は同じファイルに配置可

### エラーハンドリング
```go
// domain/errors/errors.go
type DomainError struct {
    Code    string
    Message string
    Cause   error
}

// application/errors/errors.go
type ApplicationError struct {
    Code       string
    Message    string
    StatusCode int
    Cause      error
}
```

### ロギング
```go
// shared/logger/logger.go
type Logger interface {
    Debug(msg string, fields ...Field)
    Info(msg string, fields ...Field)
    Warn(msg string, fields ...Field)
    Error(msg string, fields ...Field)
}

// 使用例
logger.Info("Problem generated",
    zap.String("user_id", userID),
    zap.String("mode", mode),
    zap.Duration("duration", duration),
)
```

## 🔄 リスク管理

### リスク1: 既存機能の破壊
**影響度**: 高
**対策**:
- 各Phase後に回帰テストを実施
- 本番環境への適用前にステージング環境で検証
- ロールバック手順の事前準備

### リスク2: パフォーマンス劣化
**影響度**: 中
**対策**:
- ベンチマークテストの実施
- プロファイリングによるボトルネック特定
- 必要に応じてキャッシュ戦略の導入

### リスク3: スケジュール遅延
**影響度**: 中
**対策**:
- 週次で進捗確認
- 優先度の低い機能は後回し
- バッファ期間の確保

### リスク4: チーム理解不足
**影響度**: 低
**対策**:
- 定期的な勉強会の開催
- ペアプログラミングの実施
- ドキュメントの充実
